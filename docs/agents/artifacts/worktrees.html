Un repo, varios agentes

Cómo git worktree le da a cada agente su propia rama — y qué sigue compartido igual, que es donde aparecen los errores.

Estado hoy — newhaze-webapp

WorktreeRamaPuerto.env.localnode_modules
newhaze-webapp stg 3000 propio sí
.claude/worktrees/issue-194 docs/194-organizaciones-fantasma 3001 · config viejo symlink sí
.claude/worktrees/pedidos-b2b-whatsapp feat/pedidos-b2b-whatsapp 3002 · config viejo symlink sí

El puerto por worktree ya está escrito en .worktree-port de los tres, pero el playwright.config.ts que lo lee vive sólo en la rama stg. Hasta que ese cambio llegue a las otras dos ramas, ellas siguen resolviendo 3000 fijo.

El problema

Un working tree tiene un solo HEAD

Un repositorio git clonado de la forma normal tiene un directorio de trabajo, y ese directorio tiene un HEAD: la rama que está checkouteada ahora. No es una convención ni un default configurable — es la estructura.

Cuando dos agentes comparten ese directorio, el git checkout del primero reescribe los archivos que el segundo está leyendo. No hay disciplina que lo arregle.

El mecanismo

Qué separa un worktree, exactamente

git worktree divide en dos lo que un clon normal tiene junto. Por un lado, el repositorio: objetos, refs, remotes, historia — sigue siendo uno solo, en un único .git. Por el otro, el working tree: los archivos en disco, el índice y el HEAD — de esos hay uno por directorio.

Por eso no cuesta casi nada: no duplica la historia ni vuelve a bajar del remote. Sólo checkoutea archivos.

Dónde se rompe

Lo que git no copia

Acá está el 90 % de los errores. Un worktree nuevo se puebla con lo que git tiene versionado. Todo lo que está en .gitignore simplemente no existe del otro lado — y es precisamente lo que la app necesita para arrancar.

El arreglo

# credenciales: symlink relativo, no copia — así siguen a la fuente
ln -sfn ../../../.env.local .claude/worktrees/<wt>/.env.local

# dependencias: instalación propia por worktree
(cd .claude/worktrees/<wt> && npm install)

El symlink es preferible a copiar: cuando rote una credencial, los tres worktrees la ven al instante. node_modules no se puede symlinkear con la misma tranquilidad — los binarios compilados y la resolución de módulos dependen de la ruta real.

El error silencioso

Dos agentes, un puerto

Este es el peor de todos, porque no falla: miente. Playwright levanta el dev server con reuseExistingServer, que significa «si ya hay algo escuchando en el puerto, usalo». Con los dos worktrees apuntando a 3000, el segundo agente encuentra ocupado el puerto y reusa la app del primero.

Sus tests corren, pasan o fallan, y reportan sobre el código de la otra rama.

La pregunta siguiente

¿No alcanzaría con un container por agente?

Un container aísla el sistema operativo: procesos, puertos, red, dependencias. No aísla git. Si dos containers montan el mismo directorio del host, adentro sigue habiendo un working tree con un solo HEAD, y los agentes se pisan igual que antes — ahora con una capa más entre el error y vos.

Las dos herramientas no compiten: resuelven capas distintas y se combinan.

Operación

Las reglas de la casa

Una rama vive en un solo worktree

Git rechaza checkoutear la misma rama en dos worktrees. No es una limitación: es la colisión que querés evitar, detectada temprano.

Todo lo ignorado se provisiona a mano

.env.local, node_modules, .worktree-port. Si la app no arranca en un worktree nuevo, empezá por acá antes de sospechar del código.

Los recursos de máquina siguen siendo uno

El stack local de Supabase es único: dos agentes migrando en paralelo se pisan, worktrees o no. Ese trabajo se serializa o se mueve a branches de Supabase.

Un cambio de config no viaja solo

Arreglar playwright.config.ts en una rama no lo arregla en las otras. Los archivos versionados se propagan por merge, como cualquier commit.

Comandos de referencia 
# crear un worktree con rama nueva
git worktree add .claude/worktrees/<nombre> -b <rama>

# ver todos los worktrees del repo y en qué rama está cada uno
git worktree list

# eliminar uno cuando terminó el trabajo
git worktree remove .claude/worktrees/<nombre>

# limpiar registros de worktrees borrados a mano
git worktree prune

En Claude Code, EnterWorktree hace el add y muda la sesión al directorio nuevo; al cerrar pregunta si conservarlo. Para subagentes, isolation: "worktree" le da a cada uno el suyo y lo limpia si no cambió nada.

Los worktrees de Claude Code viven en .claude/worktrees/ y ramifican desde origin/<default-branch>. Para que salgan del HEAD local: worktree.baseRef: "head" en .claude/settings.json.
