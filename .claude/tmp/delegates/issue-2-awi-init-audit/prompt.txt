**Current behavior:**
`/initialize` runs a 108-line Python script (`init_workspace.py`) that creates a folder structure, writes a hardcoded `CLAUDE.md`, runs `git init`, and prints next steps. It does not read from any config files, does not handle collaborator state, and the folder layout it creates is partially stale. `/awi-sync` has no awareness of whether the current user should push to `awi-core` — it either always tries or always skips, producing spurious errors.

---

**Required behavior:**

### 1. Folder scaffold from template
`/initialize` reads the expected AWI directory structure from the awi-core template at runtime — no hardcoded folder names or file contents. Output matches the current canonical layout.

### 2. `user-config.json` schema
Define two new fields in the user config schema (located at `_data/users/<github-id>/user-config.json`):
- `awi_upstream_branch` (string) — the awi-core branch this instance tracks for upstream pulls (e.g. `prod`, `stg`, `dev-claude`, `dev-gemini`). Written at user setup/config time by the user management skill, not by `/initialize`.
- `collaborator` (bool) — whether this user has write access to `awi-core`. Written at user setup/config time.

Document these fields in whatever schema reference exists for `user-config.json`.

### 3. Config regeneration on init, user switch, and logout
`/initialize` regenerates instance-level derived configs by reading the active `user-config.json` and active org config files — it does not prompt or write to `user-config.json`. The same regeneration must be triggered automatically when the user switches accounts or logs out (hook into the `/awi-user` switch and logout flows).

### 4. `.awi-source` boundary file
Introduce a `.awi-source` config file at the repo root that declares which submodule paths are owned by awi-core (e.g. `_system/agency-agents`). This file is committed to awi-core and pulled downstream via upstream sync.

The `.gitignore` generator must consult `.awi-source` when deciding what to exclude: instance-level `.gitmodules` changes are excluded; source-level submodule entries are preserved. This prevents collaborators from accidentally pushing `.gitmodules` and breaking other instances, while keeping awi-core's own submodule pointers intact.

### 5. `/awi-sync` three-state collaborator push logic
Replace the current unconditional push (or skip) with:
- `user-config.collaborator` absent or `false` → skip push to `awi-core`, no message
- `user-config.collaborator: true` but `gh api` confirms no write permission → `Warning: collaborator flag is set but awi-core write access could not be confirmed`
- `user-config.collaborator: true`, permission confirmed, push fails → `Error: push to awi-core failed`
